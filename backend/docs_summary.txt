PRAMAN AI — Product Requirements Document
SIH 2026 • SIH26034 • Final Product Specification
Purpose: define what PRAMAN AI is, who it serves, what the MVP must do, and how success will be demonstrated. This document is grounded in the submitted SIH concept: AI-assisted package/label inspection, OCR + AI extraction, rule-based validation, Computer Vision, explainable results, evidence-backed reporting, senior-friendly UX and an enforcement dashboard.
1. Product Vision
PRAMAN AI is an AI-assisted Legal Metrology inspection platform that converts product/package images into structured declarations, configurable compliance checks, visual findings, traceable evidence and reviewable inspection reports.
2. Problem
Manual inspection is time-consuming and inconsistent. Officers may need to inspect labels, verify mandatory declarations, assess readability and prepare records manually. PRAMAN aims to reduce repetitive effort while keeping the inspector in control.
3. Goals
Reduce manual label-reading effort.
Extract declarations from package images using OCR/AI.
Validate extracted information using a deterministic, configurable rule engine.
Detect visual issues using Computer Vision where technically feasible.
Show explainable, evidence-linked findings.
Support human confirmation/rejection/manual review.
Generate evidence-backed reports.
Provide inspection history, analytics and an enforcement dashboard.
Provide a simplified consumer-facing scan mode.
4. Non-Goals
Do not replace the authorized inspector.
Do not make unsupported legal claims.
Do not make an LLM the compliance decision engine.
Do not require a complex microservice/MLOps platform for the MVP.

10. MVP Acceptance Criteria

3. Core Pipeline
Image → OpenCV quality/preprocessing → PaddleOCR/DBNet++ → structured declarations → deterministic rule engine → Computer Vision checks → findings + evidence → human review → report → PostgreSQL/history.
4. Rule Engine Principle
The LLM must not be the compliance authority. Rules should be explicit, versioned and auditable. Example outputs: PASS, WARNING, POTENTIAL_VIOLATION, MANUAL_REVIEW.
5. AI/LLM Usage
Good: OCR normalization, structured field cleanup, human-readable explanation grounded in stored evidence.
Bad: asking an LLM to decide legal compliance directly from an image.
If an LLM is used, isolate it behind a provider interface so the core system remains deterministic.
6. Database Entities
users, roles, inspections, products, inspection_images, ocr_results, declarations, rules, rule_versions, compliance_checks, findings, evidence, review_decisions, reports, audit_events.

8. Project Structure
frontend/ (React, components, pages, API client, charts, evidence viewer) and backend/ (FastAPI routes, models, schemas, services, ocr, vision, rules, compliance, reports, auth, database, tests). Keep domain logic out of route handlers.
9. Deployment
Dockerize frontend/backend.
Use managed PostgreSQL.
Use object storage for images/reports.
Use HTTPS.
Start with a simple deployment; add asynchronous workers only if analysis time requires them.
10. Optional Later, Not MVP
Redis + Celery for long-running jobs.
Advanced model serving.
Dedicated vector database only if a real retrieval use case emerges.
More sophisticated observability/MLOps as scale requires.
11. Explicitly Avoid for SIH MVP
Node.js backend
MongoDB as primary database
Kubernetes
Kafka
Elasticsearch
Unnecessary microservices
LangChain everywhere
Multiple LLM providers
Complex MLOps platform
These technologies can be valid in other products, but they do not make PRAMAN automatically better. Adding them without a concrete requirement increases complexity and creates unnecessary examiner questions.
12. Examiner-Friendly Architecture Answer
“We kept the prototype aligned with our submitted architecture: React for the inspection interface, FastAPI and Python for APIs and AI/CV integration, PaddleOCR/DBNet++ for text extraction, OpenCV for image analysis, a deterministic rule engine for compliance checks, PostgreSQL for structured inspection records, and cloud infrastructure for deployment. Supporting frontend libraries improve the UI without changing the core architecture.”
13. Engineering Priority
Build the vertical slice first: upload → OCR → structured fields → rules → evidence → review → report. Only after that works reliably should advanced analytics, asynchronous processing or additional AI capabilities be added.

16. Design Anti-Patterns
Do not build a generic AI SaaS dashboard.
Do not make the chatbot the product.
Do not use huge decorative animations.
Do not hide evidence behind multiple clicks.
Do not use red/green without labels.
Do not make unsupported compliance claims.
Do not create decorative charts with no drill-down.
17. Final Direction
NeuroBank-inspired dashboard clarity + government-tech trust + computer-vision evidence workspace + field inspection UX. The defining visual experience is the inspection analysis/evidence screen, not the dashboard alone.
