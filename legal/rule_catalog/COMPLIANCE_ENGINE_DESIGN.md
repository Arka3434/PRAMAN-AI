# Deterministic Compliance Rules Engine Design (Phase 6B.1)

## 1. Overview and Purpose

The **PRAMAN Deterministic Compliance Rules Engine** is a framework-independent, rule-driven evaluation service designed to assess package inspection evidence against the versioned statutory provisions defined in `legal/rule_catalog/rules_v1.json`.

### Core Architectural Principles
1. **Deterministic Execution**: Given identical input declarations and inspection context, the engine must produce identical evaluation results. No stochastic processes, network calls, or LLM prompts are permitted.
2. **Separation of Evidence and Legal Adjudication**: OCR and computer vision produce *evidence* (text, bounding boxes, confidence); the rules engine evaluates compliance against statutory rules; the field inspector retains *final adjudicative authority*.
3. **Traceability and Auditability**: Every finding must trace directly to a specific rule ID, statutory citation, and source PDF document in the catalog.
4. **Execution Guardrails**: Only rules verified as `SAFE` may produce automated violation determinations. Rules marked `NEEDS_VERIFICATION` remain non-executable for automated failure.

---

## 2. Rule Loading and Catalog Versioning

### Rule Loading Mechanism
- **Catalog Source**: `legal/rule_catalog/rules_v1.json` (or configured catalog version path).
- **Loader Lifecycle**:
  - The catalog is loaded at service startup into immutable in-memory rule specification structures.
  - A SHA-256 digest of the catalog file is computed upon load to guarantee runtime integrity.
  - The schema of each rule is strictly validated against the mandatory contract:
    - `rule_id`, `title`, `legal_citation`, `source_document`, `effective_from`, `effective_to`, `applicability`, `exemptions`, `input_fields`, `check_type`, `expected_condition`, `severity`, `executable_status`, `evidence_requirement`.
- **Deterministic Evaluation Order**: Rules are evaluated sequentially in canonical order sorted by `rule_id` (`PCR-001` through `PCR-008`).

### Version Tracking
- Each evaluation run records the active `catalog_version` (e.g., `1.0.0`) and `catalog_hash`.
- Findings generated by the engine store the governing catalog version, ensuring complete auditability if legal rules change over time.

## 4. Applicability and Exemption Handling

Applicability is evaluated deterministically before individual rule verification:

### 4.1 General Chapter II Filter (Rule 3)
- **Condition A (Bulk Quantity)**: If declared package quantity exceeds 25 kg or 25 L (and commodity is not cement, fertilizer, or farm produce up to 50 kg), Chapter II provisions do not apply.  
  &rarr; Status: `NOT_APPLICABLE` for all Chapter II rules.
- **Condition B (Institutional/Industrial)**: If `consumer_type` is `"industrial"` or `"institutional"`, package is exempt from retail declarations.  
  &rarr; Status: `NOT_APPLICABLE`.

### 4.2 Provision-Specific Applicability
- **PCR-002 (Country of Origin)**:
  - Applicable only if `is_imported == True` or importer keywords (`importer`, `imported by`) appear in extracted text.
  - If domestic: Status evaluates to `NOT_APPLICABLE`.
- **Food / Cosmetic / Seeds Statutory Deferrals**:
  - `PCR-001` (Explanation III) and `PCR-005` (Proviso 1) defer food declarations to the Food Safety and Standards Act, 2006.
  - If `commodity_category == "food"`, the engine flags statutory deferral and routes to `MANUAL_REVIEW` or applies FSSA-compliant presence checks without misciting PCR as the sole statutory authority.

## 5. SAFE vs. NEEDS_VERIFICATION Execution Guardrails

| Status | Rules | Execution Behavior in Engine |
|---|---|---|
| **`SAFE`** | `PCR-001`, `PCR-002`, `PCR-003`, `PCR-004`, `PCR-005`, `PCR-007` | **Automated Execution Enabled**.<br>Evaluates presence, syntax, units, and formats deterministically. Can produce `PASS`, `POTENTIAL_VIOLATION`, or `WARNING`. |
| **`NEEDS_VERIFICATION`** | `PCR-006`, `PCR-008` | **Non-Executable for Automated Violations**.<br>Never generates a `POTENTIAL_VIOLATION` automatically. If evidence is detected (e.g., date string or panel box), runs optional format validation and marks status as `MANUAL_REVIEW` with an advisory explanation. |

### Rationale for Guardrails:
- `PCR-006` (Best Before): Perishability cannot be determined purely from raw image pixels without domain taxonomy.
- `PCR-008` (Principal Display Panel & Font Height): Absolute font height in millimeters cannot be determined without physical dimensional scale calibration (DPI/pixel-to-millimeter reference).

## 6. Evaluation Status Definitions

The engine assigns one of five deterministic statuses to each evaluated rule:

1. **`PASS`**:
   - All statutory declaration criteria (presence, approved units, valid date format, MRP tax statement) are satisfied.
   - Projected finding (if logged): `severity = "pass"`, `status = "resolved"`.
2. **`POTENTIAL_VIOLATION`**:
   - A mandatory statutory declaration is absent, improperly formatted, or violates metric rules on a verified `SAFE` rule.
   - Projected finding: `severity = rule.severity` (`critical` / `major`), `status = "open"`.
   - Title: `"[Rule ID]: Statutory declaration missing or invalid"`.
3. **`WARNING`**:
   - Declaration is present but has low OCR confidence (< 0.60), non-standard punctuation, or potential ambiguity that does not clearly constitute a statutory breach.
   - Projected finding: `severity = "warning"`, `status = "open"`.
4. **`MANUAL_REVIEW`**:
   - Rule is marked `NEEDS_VERIFICATION` (e.g., `PCR-006`, `PCR-008`) or statutory applicability cannot be definitively resolved from available evidence.
   - Projected finding: `severity = "warning"`, `status = "open"`, title annotated with `"[Review Required]"`.
5. **`NOT_APPLICABLE`**:
   - The commodity or package is statutorily exempt (e.g., domestic product for `PCR-002`, Rule 3 bulk exemption).
   - No adverse finding is generated.

## 7. Evidence Linkage

Every rule evaluation must maintain a verifiable evidence trail:
- **`detected_value`**: The exact normalized text extracted from the OCR result (or `null` if missing).
- **`evidence_references`**: Array of source references linking to:
  - Source image filename (e.g., `sample_front.jpg`).
  - Image capture side (`front`, `back`, `side`, etc.).
  - Bounding box coordinates (`[ymin, xmin, ymax, xmax]`) of the matched text.
  - OCR extraction confidence score.
- This ensures that in the UI review workflow, clicking a finding highlights the corresponding bounding box on the package photograph.

---

## 8. Severity Handling

Severities are anchored strictly to the statutory importance declared in `rules_v1.json`:

- **`critical`**:
  - `PCR-001`: Omission of manufacturer, packer, or importer identity and address.
  - `PCR-002`: Omission of country of origin on imported packaged goods.
  - `PCR-004`: Omission of net quantity or use of non-standard non-metric units.
  - `PCR-007`: Omission of retail sale price or failure to declare MRP inclusive of all taxes.
- **`major`**:
  - `PCR-003`: Omission of common or generic commodity name.
  - `PCR-005`: Omission or improper formatting of manufacturing month/year.
- **`warning`**:
  - Low-confidence OCR detections or advisory checks (`PCR-008` layout).

---

## 9. Auditability and Integrity Assurance

1. **Immutable Rule Specifications**: The catalog is read-only. Dynamic rule modification at runtime is prohibited.
2. **Deterministic Regression Test Suite**: A suite of reference declaration fixtures (valid packages, missing address, missing MRP, imported goods, exempt goods) tests engine output for exact identity on every build.
3. **Zero Model Hallucination**: No generative LLM or heuristic model has authority over rule pass/fail logic. All evaluations are pure functions of the input dictionary.
4. **Clean Decoupling from API & Database**: The engine is a standalone domain service (`ComplianceEngine.evaluate(...)`) accepting plain data structures and returning plain results. It does not depend on FastAPI or SQLAlchemy, allowing independent verification.
